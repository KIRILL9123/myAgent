# GitHub OSS-аудит для Mira — 2026-08-04

Статус: завершённый аудит, новых runtime-зависимостей по итогам не добавлено.

Цель аудита — найти зрелые решения для личного local-first ассистента, но не
превратить Mira в набор склеенных мини-приложений. Проверялись не только идеи,
но и совместимость с доменной архитектурой, лицензия, размер внедрения,
локальность данных и риск дублирования существующих сервисов.

## Решение

Ничего не подключать целиком. Mira уже владеет своими сущностями, registry,
approval flow, SQLite-схемой и notification projection. GitHub-проекты
используем как источники архитектурных паттернов и, только если это оправдано,
как небольшие MIT-лицензированные adapter-level компоненты.

## Извлечённые идеи, которые сохраняем

Ниже не список задач «скопировать проект», а набор проверенных паттернов,
которые уже привязаны к существующим доменам Mira.

### Document Vault: pipeline вместо одного extractor

**Источник:** [paperless-ngx](https://github.com/paperless-ngx/paperless-ngx),
включая его [OCR configuration](https://github.com/paperless-ngx/paperless-ngx/blob/dev/docs/configuration.md).

Сохраняем следующие идеи:

- разделять original file, archive/search representation и metadata;
- делать deduplication по хешу до дорогой обработки;
- иметь явные статусы ingestion (`ready`, `failed`, в будущем `processing`);
- хранить язык, режим OCR, extractor и ошибку как provenance metadata;
- ограничивать страницы, размер изображения, время и языки до запуска OCR;
- не отправлять OCR-результат напрямую в задачи/календарь: сначала FTS5,
  evidence и Approval Center.

Не переносим Paperless server, Redis, Django/Angular UI и его database model.

### Memory и Assistant: retrieval должен быть объяснимым

**Источник:** [Khoj](https://github.com/khoj-ai/khoj).

Берём как направление:

- отдельное решение «нужно ли искать в Memory/Document Vault» перед дорогим
  retrieval;
- ответы с явным источником и bounded context;
- scheduled research/summary как отдельный delivery job, а не скрытая логика
  внутри обычного чата;
- настраиваемые skills/agents поверх общего tool registry.

В Mira это уже частично выражено через Retrieval Gate, Evidence Bundle,
Procedural Memory и общий Tool Registry. Следующая эволюция — улучшать
объяснимость и качество retrieval, не подключая второй memory engine.

### Tasks и Focus: сначала view, потом новые сущности

**Источники:** [Super Productivity](https://github.com/super-productivity/super-productivity)
и [Vikunja](https://github.com/go-vikunja/vikunja).

Полезные продуктовые идеи:

- Focus mode как временный режим отображения/уведомлений, а не отдельный
  task-домен;
- timeboxing как явная связь существующего Commitment с Calendar event;
- проектная группировка и recurring task views как projections;
- стабильные identity/links для Goal → Project → Task → Commitment.

Запрещённая shortcut-реализация: не создавать параллельные `tasks`, `projects`
и `goals` только ради нового экрана. Сначала proposal и миграция поверх
Commitments.

### Finance: budgets как отдельный слой над ledger

**Источник:** [Actual Budget](https://github.com/actualbudget/actual) и его
[MIT license](https://github.com/actualbudget/actual/blob/master/LICENSE.txt).

Сохраняем идею разделения:

- ledger transactions остаются неизменяемой историей;
- budgets/accounts/targets должны быть отдельными сущностями или read models;
- бюджетная классификация не должна переписывать исходную валюту операции;
- sync/client concerns не должны попадать в локальный Finance service.

Это не активная реализация: сначала нужен реальный сценарий использования
бюджетов в личном workflow и отдельный Finance proposal.

### Workspace и Agent UX: прозрачные capability surfaces

**Источники:** [AppFlowy](https://github.com/AppFlowy-IO/AppFlowy) и
[LobeHub](https://github.com/lobehub/lobehub).

Полезно наблюдать:

- workspace navigation, где документы, проекты и контекст видны рядом;
- явные skills/tool surfaces вместо магических скрытых возможностей;
- mobile-first сокращение действий до Chat, Tasks, Notifications и Upload;
- preview контекста перед тем, как он влияет на ответ или действие.

В Mira это остаётся UI/UX reference. Код, agent marketplace и custom-license
слои LobeHub не принимаются в зависимость.

### Calendar: provider abstraction важнее нового сервера

**Источник:** [Radicale](https://github.com/Kozea/Radicale).

Radicale подтверждает ценность маленького local CalDAV provider, но Mira уже
имеет provider contract и единый `calendar_service`. Поэтому идею сохраняем как
операционный fallback для полностью локального режима, а не как новую
обязательную инфраструктуру.

## Что реально взять

### 1. OCR для Document Vault — следующий кандидат

Paperless-ngx подтверждает правильное направление для следующей документной
итерации: сначала безопасный intake, затем extraction/OCR, затем поиск и только
после этого domain proposals. Для Mira это означает небольшой адаптер внутри
`document_service.py`, а не импорт Paperless:

- определить image-based PDF и изображения без извлечённого текста;
- запускать локальный OCR только при включённой настройке;
- ограничить размер, страницы, языки и время выполнения;
- сохранять способ извлечения и уверенность в `metadata`, не менять
  исходный файл;
- прогонять результат через существующие chunks, FTS5, provenance и Approval
  Center;
- при ошибке оставить документ в `failed`, не создавать тихих задач/событий.

Это закрывает конкретный пункт roadmap — OCR для сканов — и не создаёт новый
домен.

### 2. Project hierarchy — после подтверждения реальной потребности

Super Productivity и Vikunja показывают, что Goals → Projects → Tasks —
полезная модель, но сейчас Mira уже имеет Commitments, Calendar links, Today и
Action Center. Поэтому сначала нужен proposal и миграционный план, а не новый
параллельный task manager.

### 3. Finance Budgets — позже

Actual Budget полезен для UX envelope budgeting и разделения финансовых слоёв,
но добавление accounts/budgets/exchange-rate history сейчас расширит Finance
сильнее, чем нужно личному сценарию. Возвращаться к этому стоит после нескольких
реальных циклов использования текущих transactions/recurring templates.

## Почему не копируем готовый продукт

Даже когда лицензия разрешает использование, перенос целого проекта ломает
главный контракт Mira: одна доменная модель, один источник истины, единый
Assistant/Telegram registry и локальный approval flow. Поэтому правило остаётся
таким же, как в [OSS_INTEGRATIONS.md](OSS_INTEGRATIONS.md): принимаются только
изолированные компоненты с понятным adapter boundary, тестом удаления и
явно сохранённой лицензией.

## Следующий шаг

Следующая реализация — OCR v1 для сканов и изображений в существующем Document
Vault. До написания кода нужно проверить, какие локальные OCR-бинарники доступны
на машине, выбрать минимальный adapter contract и добавить feature proposal;
Paperless-ngx остаётся reference implementation, а не новой зависимостью.
